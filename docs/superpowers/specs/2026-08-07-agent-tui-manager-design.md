# Agent TUI Manager 设计规格

日期: 2026-08-07

## 1. 产品目标

Agent TUI Manager 是一个本地桌面工作台，用于同时运行和管理多个终端型 Agent。用户可以在一个窗口中启动 Codex、Claude Code、Pi 和自定义 CLI Agent，查看实时状态，处理授权请求，恢复异常中断，并加载各 Agent 自己保存的历史会话。

首版面向 Windows，重点优化 2 到 6 个并发 Agent。平台相关能力必须通过接口隔离，为以后支持 macOS 和 Linux 保留实现空间。

### 1.1 核心价值

- 不再频繁切换多个终端窗口检查 Agent 状态。
- 在 Agent 总览中直接处理常见授权和恢复事件。
- 对低风险重复授权生成可控的自动批准规则。
- 明确区分正常完成、用户停止和异常中断，避免错误 Continue。
- 保持 Codex、Claude Code 等工具原有的会话存储和命令行工作流。

### 1.2 首版不做

- 不提供账号、云同步或远程服务。
- 不把 Agent 会话转换为 Manager 私有格式。
- 不直接接管或重新挂接已经运行的外部终端 PTY。
- 不自动创建 Git Worktree，也不自动合并多 Agent 修改。
- 不为 Pi 和任意自定义 CLI 提供未经验证的智能审批。
- 不在首版同时交付 macOS 和 Linux 应用。

## 2. 不可违反的会话所有权约束

Manager 永远不是 Agent 会话的所有者。Codex、Claude Code 和其他 Agent 的原生会话存储是唯一权威数据源。

必须满足以下不变量:

1. Manager 通过正常 CLI 入口启动 Agent，不修改 `CODEX_HOME`、Claude Code 数据目录或用户的原生配置根目录。
2. 只有 Agent CLI 自己读写其原生会话文件。Manager 优先调用官方历史和恢复能力；需要建立索引时只读原生元数据。
3. 对 Agent 会话而言，Manager 数据库只保存引用和界面元数据，例如 Agent 类型、工作区、原生会话 ID、显示名称、布局和最近状态。Manager 自己的审批规则和应用设置仍保存在 Manager 数据库中。
4. 删除或损坏 Manager 数据库后，用户仍能进入原工作区，使用 `codex resume`、`claude --resume` 或对应 Agent 的原生命令恢复会话。
5. Manager 重装后可以重新扫描原生会话并重建工作区索引。重建不依赖旧的 Manager 数据库。
6. Manager 内创建的会话可被原生 CLI 恢复；原生 CLI 创建的会话也可被 Manager 发现和恢复。
7. Manager 保存的终端输出日志仅用于查看和诊断，不参与 Agent 上下文恢复，也不能成为恢复所必需的数据。

最坏情况下，进程在 Agent CLI 完成持久化之前崩溃，可能丢失崩溃瞬间尚未写入的少量输入或输出。Manager 不得造成整个原生会话丢失，也不得让恢复依赖 Manager 私有数据。

## 3. 技术路线

首版采用以下技术栈:

- Electron: 桌面容器、主进程和 Windows 系统集成。
- React + TypeScript: 用户界面和状态投影。
- xterm.js: ANSI、光标、键盘和 TUI 渲染。
- node-pty: Windows ConPTY 进程承载。
- SQLite: Manager 自己的工作区、规则、索引和事件元数据。
- Windows Named Pipes: 桌面进程与独立会话宿主之间的本地 IPC。
- Windows Credential Manager: 必须由 Manager 保存的敏感凭据。普通 Agent 凭据仍由 Agent 自己管理。

选择 Electron 的原因是终端和 PTY 生态成熟，能够优先降低 Codex、Claude Code 等交互式 TUI 的兼容风险。Electron 基础资源开销相对较高，但在同时运行多个 Agent 的目标场景中不是主要资源来源。

## 4. 系统边界

### 4.1 Desktop Shell

负责窗口、托盘、通知、任务栏状态和安全 IPC。Renderer 不直接获得任意 Node.js 或操作系统权限。

### 4.2 Session Orchestrator

每个 Agent 会话的唯一 Manager 状态源。它协调创建、停止、恢复、迁移和重连，并把各 Agent 的事件投影成统一状态。

Orchestrator 不解析终端屏幕来盲目发送按键。审批或自动恢复必须来自适配器提供的结构化证据。

### 4.3 Session Host

每个活跃 Agent 由独立的轻量本地会话宿主承载。Session Host 持有 PTY、Agent 子进程和终端缓冲区，通过 Named Pipe 与桌面应用通信。

- Renderer 或 Electron 主进程崩溃时，Session Host 默认继续运行。
- Manager 重启后先发现并重连仍存活的 Session Host。
- Session Host 也不存在时，Manager 才使用 Agent 原生会话 ID 执行恢复。
- Session Host 不是会话权威数据源。删除全部 Session Host 和 Manager 数据后，原生 CLI 恢复仍必须可用。
- 用户关闭窗口时默认最小化到托盘。用户明确选择退出时，可选择保留活跃 Session Host 或停止 Agent；任何选择都不能删除原生会话。

### 4.4 PTY Host

Session Host 内部通过 node-pty 创建 ConPTY，负责:

- 启动真实 Agent CLI。
- 双向传输字节流和键盘输入。
- 同步终端窗口尺寸。
- 记录退出码、退出信号和进程树事实。
- 对输出实施有界缓冲和背压，避免高输出 Agent 阻塞界面。

PTY Host 只报告事实，不独立判断任务是否完成或是否应该 Continue。

### 4.5 Agent Adapters

所有 Agent 通过统一适配器接口接入:

- 检测本机安装和版本。
- 构建新会话和恢复会话命令。
- 发现当前工作区相关的原生历史会话。
- 将官方可机读事件转换为统一状态、授权和错误事件。
- 判断当前 CLI 版本是否支持智能审批和可靠恢复。

首版支持深度适配 Codex 和 Claude Code。Pi 及其他命令使用 Generic CLI Adapter，只保证终端、启动、停止和用户显式配置的恢复命令。

未知或未验证的 Codex、Claude Code 版本自动降级为普通终端和人工处理，不启用智能审批。

### 4.6 Approval Policy Engine

接收适配器提供的结构化请求，解析命令并按风险、路径、工作区和用户规则决策。它不能仅通过屏幕文本、按钮位置或简单字符串包含关系批准请求。

### 4.7 Native Session Discovery

按 Agent 类型发现原生会话，并按工作区聚合。Manager 应优先使用官方 CLI 或稳定的公开元数据；不得修改原生历史文件。

### 4.8 Local Store

SQLite 仅保存 Manager 元数据:

- 工作区和最近使用记录。
- Agent 配置模板和自定义命令。
- 原生会话引用和可重建索引。
- 审批规则、决策原因和审计记录。
- 通知状态、界面偏好和终端日志索引。

## 5. 用户体验

### 5.1 首页: 终端墙

首页以 2 到 6 个 Agent 的实时终端为主体。

- 2 到 4 个 Agent 默认使用稳定的网格布局。
- 5 到 6 个 Agent 使用响应式网格，保持每个终端可扫描。
- 每个终端卡片固定展示 Agent、任务名、运行时间和状态。
- 点击放大按钮进入单 Agent 全屏终端，再返回总览。
- 总览展示运行中、等待授权、正在恢复、已完成、失败和已停止状态。
- 多个 Agent 共享同一工作区。检测到两个活跃 Agent 修改同一文件时提醒，但首版不阻止写入、不自动创建 Worktree。

### 5.2 添加 Agent

“新建 Agent”在终端墙右侧打开面板，工作区默认继承当前项目。面板有三个标签:

1. 新会话: 选择 Codex、Claude Code、Pi 或自定义命令，并选择审批策略。
2. 恢复历史: 展示当前工作区的原生历史，支持按 Agent、标题、会话 ID 和内容索引搜索。
3. 迁移外部会话: 识别外部进程、工作区和可能匹配的原生会话。

### 5.3 外部会话迁移

Windows 无法可靠地把任意外部终端的 PTY 和实时画面重新挂接到 Manager。迁移采用恢复语义:

1. Manager 尽力检测已运行的 Codex 或 Claude Code 进程、工作目录和原生会话。
2. 用户选择“准备迁移”。
3. Manager 等待用户在原终端正常停止 Agent，不强制向不受控制的终端注入 Ctrl+C 或 Enter。
4. 检测到原进程退出后，在 Manager 的 Session Host 中通过原生命令恢复同一会话。
5. 无法可靠匹配会话时，引导用户从当前工作区的原生历史中选择。

这避免两个进程同时操作同一个原生会话。

### 5.4 总览内审批

Agent 总览是日常审批的主入口:

- 低风险请求在对应终端卡片底部展示“拒绝”和“批准”操作。
- 第三次批准后的记忆建议以不改变终端网格尺寸的轻量提示出现。
- 删除、覆盖、提权和工作区外写入等高风险请求从卡片打开详情抽屉，展示命令、影响范围和不可恢复性后再处理。
- 高风险请求不能在卡片中使用单击直接批准。

处理中心不是必经页面。它用于跨 Agent 汇总、低风险批量处理、异常队列、审批历史和规则管理。

### 5.5 后台体验

默认启用:

- 托盘常驻。
- Windows 系统通知。
- 任务栏状态或角标。

默认通知待人工授权、恢复失败和任务完成。提示音可配置，默认关闭。托盘可以打开对应 Agent 或处理中心，并执行符合安全边界的快捷操作。

## 6. 会话状态与恢复

统一会话状态包括:

- `starting`: 正在启动 Session Host 或 Agent。
- `running`: Agent 正常运行。
- `needs_approval`: 等待用户处理授权。
- `recovering`: 已确认异常，正在按策略恢复。
- `completed`: Agent 明确完成并正常退出。
- `stopped`: 用户主动停止。
- `failed`: 异常恢复达到上限。
- `unknown`: 证据不足，需要人工判断。

### 6.1 正常结束

深度适配的 Agent 只有在明确完成事件和正常进程退出事实一致时标记 `completed`。Generic CLI 没有结构化完成事件时，用户停止以外的退出码 0 视为正常进程完成。两种正常结束都绝不触发 Continue 或恢复。

### 6.2 用户停止

用户主动停止时记录停止意图，并标记 `stopped`。即使退出码非零，也不能把用户停止误判为异常恢复。

### 6.3 明确异常

适配器报告错误、连接断开、进程异常退出或 Session Host 明确丢失时，可以进入 `recovering`。

恢复规则:

- 每次异常最多自动尝试 3 次。
- 使用递增退避，首版为 1 秒、4 秒和 12 秒。
- 每次恢复使用 Agent 官方原生恢复命令和原生会话 ID。
- 达到上限后进入 `failed` 和处理中心，不无限循环。

### 6.4 无法判断

长时间无输出不是异常证据。状态冲突、未知退出语义或未知 CLI 版本进入 `unknown`，只提醒用户，不自动输入 Continue。

## 7. 智能审批算法

### 7.1 决策顺序

1. 接收适配器提供的结构化授权请求。
2. 使用对应 Shell 的结构化解析能力提取可执行程序、子命令、参数、管道、重定向、变量展开和目标路径。
3. 解析并规范化工作目录和所有可识别路径，处理相对路径、符号链接和 Windows Junction。
4. 先应用不可学习的高风险边界。
5. 匹配内置安全规则。
6. 匹配用户自定义规则和已确认的学习规则。
7. 未命中时进入人工处理，并记录批准指纹。

解析失败、适配器证据不足或版本不受支持时，默认人工处理。

### 7.2 内置安全规则

首版随应用提供经过测试的窄范围只读规则，例如读取文件、搜索文本、查看 Git 状态和差异。内置规则按可执行程序和子命令精确描述，不以“允许整个程序”的宽泛方式配置。

涉及插件、脚本钩子或可能执行任意代码的命令不能仅凭常见名称进入内置安全列表。

### 7.3 用户规则

用户可以创建精确命令、结构化模板或受限前缀规则。规则必须显示:

- 命令模式。
- 允许的参数位置。
- 工作区范围。
- Agent 范围。
- 路径、管道、重定向、联网和提权限制。
- 创建原因和最近命中时间。

默认作用域为当前工作区。

### 7.4 重复批准学习

同一个规范化低风险指纹在同一工作区被手动批准 3 次后，Manager 询问是否加入授权列表。

- 默认仅对当前工作区生效。
- 建议规则必须足够具体，例如 `codegraph explore <query>`，不能泛化为允许全部 `codegraph`。
- 用户可以选择仍然每次询问。
- Manager 不静默添加学习规则。
- 用户可以随时暂停、修改或撤销规则。

### 7.5 永不自动学习

以下操作不参与重复批准学习，也不能被低风险批量批准:

- 删除和递归删除。
- 覆盖或不可逆改写。
- 提权和权限变更。
- 工作区外写入。
- 未经限制的网络下载或上传。
- 下载后直接执行、管道到 Shell 或类似组合。
- 无法完整解析的复合命令。

规则系统必须在持久化和运行时都阻止学习规则覆盖这些硬边界。

## 8. 数据保留与隐私

所有数据保存在本机，不提供登录和云同步。

- Manager 终端输出默认保留 30 天。
- 用户可把保留期配置为 1 到 90 天，也可随时手动清空。
- 终端日志按会话分段保存并压缩，SQLite 只保存日志索引。
- 原生 Agent 历史不受 Manager 日志保留期影响。
- 清空 Manager 日志或数据库不能删除原生 Agent 会话。
- 审批审计记录保留命令指纹、决策和原因；敏感参数必须按规则脱敏。
- Manager 不复制完整 Agent 原生会话数据库。

## 9. 错误处理

### 9.1 Session Host 断开

Manager 先通过 Named Pipe 重连。重连失败时检查 Agent 进程和原生会话，不假设会话已经丢失。

### 9.2 Manager 崩溃

Session Host 默认继续运行。Manager 重启后枚举本机 Session Host 并恢复 UI。若宿主也不存在，则从原生历史恢复。

### 9.3 数据库损坏

启动新的 Manager 数据库，重新扫描工作区和原生会话。界面昵称、布局和自定义规则可能需要重建，但 Agent 对话必须仍可由原生 CLI 恢复。

### 9.4 Agent CLI 升级

适配器按版本声明支持能力。未知版本关闭智能审批和自动恢复语义，只保留 PTY、普通输入输出和人工操作。

### 9.5 输出过载

Session Host 使用有界缓冲，界面更新合并到稳定帧率。磁盘日志写入失败时显示告警，但不能停止 Agent 或影响原生会话。

## 10. 安全边界

- Electron Renderer 启用上下文隔离，关闭任意 Node 集成。
- Renderer 只能调用白名单 IPC。
- 会改变进程、文件或规则的 IPC 携带一次性请求标识，拒绝过期批准。
- Session Host Named Pipe 使用当前用户可访问的 ACL 和不可预测的端点标识。
- Agent 环境变量从明确配置继承，不在日志和 UI 中泄露敏感值。
- Manager 不绕过 Agent 自身权限系统，而是通过适配器选择 Agent 官方支持的授权动作。
- 自动审批决策记录匹配规则、风险结果和规范化命令，方便审计和撤销。

## 11. 测试与验收

### 11.1 单元测试

- 会话状态机所有合法和非法转换。
- 正常完成、用户停止、异常退出和未知状态的区分。
- Shell 解析、路径规范化和规则优先级。
- 高风险硬边界不能被自定义或学习规则覆盖。
- 第 3 次批准建议规则，拒绝后不静默添加。
- 日志保留和敏感参数脱敏。

### 11.2 适配器契约测试

- 每个受支持 Codex 和 Claude Code 版本使用固定事件夹具测试。
- 新会话、历史发现、原生恢复、正常完成、授权和异常事件必须符合统一契约。
- 未知版本必须可靠降级。

### 11.3 PTY 集成测试

使用可控的测试 CLI 模拟 ANSI 输出、全屏 TUI、授权提示、正常退出、异常退出、长时间静默和大量输出。

- 验证 ConPTY 尺寸、键盘、复制和 Unicode。
- 验证 2 到 6 个并发 Session Host。
- 验证 Renderer 和 Electron 主进程崩溃后的 Session Host 重连。
- 验证恢复达到上限后停止。

### 11.4 原生会话可移植性验收

这是发布阻断测试:

1. 在 Manager 内分别启动 Codex 和 Claude Code 并完成多轮交互。
2. 强制结束 Manager UI 和 Electron 主进程。
3. 验证存活的 Session Host 可被 Manager 重启后重连。
4. 结束 Session Host，删除 Manager SQLite、终端日志和索引。
5. 在原工作区通过 `codex resume` 和 `claude --resume` 恢复原会话。
6. 重装或清空 Manager 后重新扫描，验证同一原生会话可再次出现在历史列表中。
7. 从普通终端创建会话，验证 Manager 能反向发现并恢复。

任一 Agent 只能依赖 Manager 私有数据恢复时，版本不得发布。

### 11.5 端到端测试

- 从工作区创建 Codex、Claude Code、Pi 和自定义 Agent。
- 在终端墙切换、放大和返回。
- 在总览中批准低风险请求并创建学习规则。
- 高风险请求必须打开详情且不能批量批准。
- 正常退出不恢复，明确异常按 1、4、12 秒退避恢复。
- 外部迁移等待原进程退出后通过原生命令恢复。
- 托盘、通知、任务栏状态和日志清理符合设置。

## 12. 首版成功标准

首版完成需要同时满足:

- Windows 上可稳定运行 2 到 6 个真实 Agent TUI。
- Codex 和 Claude Code 的新建、历史发现和原生恢复通过契约测试。
- Pi 和自定义命令可作为基础 PTY Agent 运行。
- 总览内审批、处理中心和学习规则符合安全边界。
- 正常完成从不触发 Continue，用户停止从不触发恢复。
- 明确异常最多恢复 3 次，未知状态不自动操作。
